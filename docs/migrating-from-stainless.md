# Migrating from Stainless

Stainless joined Anthropic in May 2026 and closed new signups. If your SDKs are generated by
Stainless, you can't count on it regenerating them when your API changes. This guide moves them
to perseid while keeping their package names, registries, repositories and versions, so your
users upgrade like they would to any new major version.

## When to switch

- Your API keeps changing, and the SDKs must follow it.
- You want generation to run in your own CI, from a spec you own.
- Your SDKs are in languages perseid generates: TypeScript, Python, Go, Java and C# (and Rust).
  perseid generates no Kotlin, Ruby, PHP, CLI, Terraform provider or MCP server.

Plan it as a major release of each SDK: calls look the same in Python and mostly the same in
TypeScript, but types and some names change (see [what changes](#what-changes-for-your-users)).

## What stays the same for your users

These hold for the TypeScript and Python SDKs, checked against SDKs generated from the
[test fixture](../tests/fixtures/stainless.yml):

| | Stainless and perseid |
|---|---|
| Install | Same package names, on the same registries |
| Client | `new Knock({ apiKey })`, `Knock(api_key=...)`, `AsyncKnock` in Python |
| Environment | `KNOCK_API_KEY` and `KNOCK_BASE_URL` |
| Resources | `client.users.list()`, `client.messages.markAsArchived(id)`: method names come from `stainless.yml` for the resources whose operations perseid groups under the same name (their first tag): `client.workspaces.peers.chat()` becomes `client.peers.chat()`, but `client.sessions.peers.add()` keeps perseid's name in `client.sessions` |
| Arguments | Path parameters first, then objects (TypeScript) or keyword arguments (Python) |
| Pagination | `for await (const user of client.users.list())`, `for user in client.users.list()`, `hasNextPage()`/`getNextPage()`, `has_next_page()`/`get_next_page()` |
| Errors | `APIError`, `NotFoundError`, `RateLimitError`, `APIConnectionError`... by status, with `status` / `status_code`. `Knock.NotFoundError` works in TypeScript |
| Retry settings | Twice by default, exponential backoff from 0.5s to 8s, honoring `Retry-After`. `maxRetries` / `max_retries` on the client and per call. Which requests are retried differs: see [known differences](#known-differences) |
| Timeouts | `timeout` in milliseconds (TypeScript) or seconds (Python), on the client and per call |
| Raw responses | `.withResponse()`, `.asResponse()`, `client.users.with_raw_response.get(...)` |
| Per-client options | `client.with_options(max_retries=0)` in Python |

## What changes for your users

### TypeScript

```ts
// Stainless
import Knock from "@knocklabs/node";

const client = new Knock();
const user = await client.users.get("dnedry");
console.log(user.created_at);                       // "2026-01-01T00:00:00Z"
for await (const u of client.users.list({ page_size: 50 })) {}
try {
  await client.users.get("nobody");
} catch (err) {
  if (err instanceof Knock.NotFoundError) console.log(err.status);
}
const { data, response } = await client.users.get("dnedry").withResponse();
```

```ts
// perseid
import { Knock } from "@knocklabs/node";        // no default export

const client = new Knock();
const user = await client.users.get("dnedry");
console.log(user.createdAt);                       // a Date
for await (const u of client.users.list({ pageSize: 50 })) {}
try {
  await client.users.get("nobody");
} catch (err) {
  if (err instanceof Knock.NotFoundError) console.log(err.status);
}
const { data, response, requestId } = await client.users.get("dnedry").withResponse();
```

- `import Knock from` becomes `import { Knock } from`. Stainless SDKs already export the named
  class too (`export { Knock }`), so your users can switch their imports before the migration.
- Model properties and parameters are camelCase (`createdAt`, `pageSize`), not the JSON names.
  The SDK converts them on the wire.
- `date-time` values are `Date`s.
- Types are named after the spec's schemas and exported from the package root, without the
  resource namespaces Stainless adds.

### Python

```python
# Stainless and perseid alike
from knockapi import Knock, NotFoundError

client = Knock()
user = client.users.get("dnedry")
print(user.created_at)                              # a datetime
for u in client.users.list(page_size=50): ...
try:
    client.users.get("nobody")
except NotFoundError as error:
    print(error.status_code)
raw = client.users.with_raw_response.get("dnedry")
user = raw.parse()
```

- Models are dataclasses with `from_dict()`, `from_json()`, `to_dict()` and `to_json()`, not
  pydantic models: `model_dump()` and `model_validate()` are gone, and `to_dict()` and
  `to_json()` take no options (no `indent`, `exclude_unset` or `mode`): `to_json()` is compact,
  not indented.
- Types live in `knockapi.models`, named after the spec's schemas.
- There is no `with_streaming_response`.

### Go, Java and C#

Client construction, parameter types and option helpers differ from Stainless's. Expect your
users to change more than imports: `knock.New(token, nil)` and `client.Users().Get(ctx, id)` in
Go. See [languages](languages.md) for each SDK.

## Import stainless.yml

Run `init` where the SDKs will be generated from: the API repository, or a separate SDKs
repository (see [repository layouts](ci.md#repository-layouts)). Point it at your Stainless
config and at your spec:

```sh
npx perseid init --from stainless.yml --spec openapi.yaml
```

It asks nothing. `--sdks`, `--name`, `--repo`, `--base-url` and `--license` override what it
imports. It writes `perseid.toml` and the workflows, then lists what it did not carry over, each
with why:

```
From stainless.yml: name, sdks, packages, repositories, base_url, license, idempotency_keys, 2 pagination rules, 3 method names, exclude (1 operation)
Not carried over from stainless.yml:
  - edition: perseid has no editions: a perseid upgrade that changes the SDKs comes as a pull request
  - targets.ruby: perseid generates no Ruby SDK
  - client_settings.opts.branch: perseid clients take no custom options: send `X-Knock-Branch` with the default headers (`defaultHeaders`, `default_headers`)
  - pagination.slack_channels_cursor: `query_options.cursor` is a nested parameter: perseid pages with a top-level query parameter
  - resources.users.list_schedules: `paginated: false`, but a pagination rule matches `listUserSchedules`: set `x-pagination: false` on it in the spec
  - resources.users.feeds (1 method): nested resource: perseid has one level of resources, named after the operations' first tag: users.retrieve_feed
  ...
```

```toml
spec = "openapi.yaml"
name = "Knock"
sdks = ["typescript", "python", "go"]
base_url = "https://api.knock.app"
idempotency_keys = true
exclude = ["notify"]

[methods]
getUser = "get"
archiveMessage = "mark_as_archived"

[[pagination]]                      # entries_cursor
cursor = "after"
items = "entries"
next_cursor = "page_info.after"

[typescript]
package = "@knocklabs/node"
repo = "knocklabs/knock-node"
```

Use your own spec, not the `openapi_spec_url` of `.stats.yml`: that copy is hosted by Stainless.
Without `--spec`, `init` maps everything but the resources, and says so.

Then work through the list. Most items are fixed in the spec:

- A method in another resource: perseid groups operations by their first tag. Tag them as the
  resource is named in `stainless.yml`.
- `x-pagination: false` on an operation Stainless did not paginate.
- `components.securitySchemes` and `security` that `stainless.yml` overrode.
- Transforms of `openapi.transforms`, applied to the spec itself.

Preview the SDKs with `npx perseid generate --out /tmp/sdks`, and compare the methods each
`api.md` lists with those of the `api.md` Stainless generated.

### Config mapping

| `stainless.yml` | `perseid.toml` |
|---|---|
| `organization.name` | `name`, cased as Stainless does: `onebusaway-sdk` is `OnebusawaySDK`, `custom_casings` apply |
| `organization.docs`, `organization.contact` | `[metadata]` `homepage`, `authors` (as `organization.name`) |
| `targets.typescript` (or `node`), `python`, `go`, `java`, `csharp` | `sdks`. `skip: true` leaves one out |
| `targets.*.package_name`, `targets.java.reverse_domain` | `package` of the language table |
| `targets.*.production_repo` | `repo` of the language table, without its `#branch` |
| `targets.go.options.go_module_path_override` | `[go] module` |
| `environments` | `base_url`: the first one |
| `client_settings.default_timeout` | `timeout`, in seconds, rounded up, unless it is perseid's 60 |
| `client_settings.idempotency` | `idempotency_keys = true` |
| `client_settings.default_env_prefix`, `client_settings.opts.*.read_env` | `env_prefix` under `[context]`, when it isn't the `name`'s |
| `settings.license` | `[metadata] license`, over the spec's |
| `pagination` | `[[pagination]]`, one rule per scheme |
| `resources.*.methods` | `[methods]`, for each name perseid would give otherwise, in the resources (or the last level of nested ones) perseid names alike |
| Endpoints no resource lists, `unspecified_endpoints`, `skip: true` | `exclude`. When fewer than 80% of the endpoints `stainless.yml` lists are in the spec, it warns and excludes only `unspecified_endpoints` and `skip: true` |
| `skip` or `only` naming languages | `exclude` of the language tables |

Pagination schemes:

| Stainless | perseid rule |
|---|---|
| `cursor`: `next_cursor_param`, `next_cursor_field` | `cursor`, `next_cursor` |
| `cursor_id`: `next_cursor_id_param`, `cursor_item_id` | `cursor`, `item_cursor` (`id` by default) |
| `offset`: `offset_count_param`, `offset_total_count_field` | `offset`, `total` |
| `page_number`: `page_number_param`, `total_page_count_field` | `page`, `total_pages` |
| `items`, `has_next_page` | `items`, `has_more` |
| `cursor_url`, `fake_page`, `param_location: body` | Not supported, listed |
| `previous_cursor_*` | Not supported: perseid pages forward only |

Everything else is listed with why: `readme`, `openapi`, `query_settings` perseid does not
follow, `custom_casings`, `codeflow`, `diagnostics`, client options that are not credentials,
retry settings other than the defaults, other `environments`, and target settings such as
`publish`, `staging_repo` and `edition`.

## Keep the package names and registries

`init --from` names each package as Stainless did. Check these, which it reports:

| Registry | Check |
|---|---|
| npm | `[typescript] package` is the npm name |
| PyPI | `[python] package` is both the import name and the PyPI name. If Stainless's `project_name` differed, set `name` in the SDK's `pyproject.toml` after the first generation: perseid doesn't rewrite it |
| Go | The module path is `github.com/<repo>`. Set `[go] module` if yours ended in `/v2` or later |
| Maven Central | The group is `[java] package`. Check `POM_ARTIFACT_ID` in `gradle.properties` after the first generation |
| NuGet | `[csharp] package` is the root namespace and the package id |

perseid writes package manifests once, then leaves them to you, like the README.

## Switch CI and releases

perseid's [GitHub Action](ci.md#github-action) regenerates the SDKs when the spec changes and
opens a pull request in each SDK repository. release-please, which Stainless SDKs already use,
releases them.

1. In each SDK repository, on a branch, delete what Stainless generated. Keep `CHANGELOG.md`,
   `LICENSE`, `.release-please-manifest.json` and the code you wrote yourself. Delete
   `release-please-config.json` too: perseid writes its own, and keeps the version of the
   manifest. Merge it before the first perseid pull request: perseid doesn't write a package
   manifest into an SDK that has one.
2. Run `npx perseid sync`. It installs the perseid App on the repositories, and commits
   `sdk-release.yml` and `sdk-ci.yml` to each SDK repository. Delete Stainless's own release
   workflows there.
3. Set up publishing, as `init` printed. npm and PyPI publish with trusted publishing: add the SDK
   repository, workflow `sdk-release.yml` and environment `release` as a trusted publisher of the
   existing package. See [publishing](ci.md#publishing).
4. Commit and push `perseid.toml` and the workflows. `sdks.yml` opens the SDK pull requests.
5. Release a major version: before merging, add `!` to the pull request's title
   (`feat(api)!: ...`). The release PR then bumps the version of the manifest, so the SDK goes
   from 4.2.0 to 5.0.0.
6. Once perseid has released each SDK, uninstall the Stainless GitHub App and archive the staging
   repositories.

Code you added to files Stainless generated is lost when they are deleted. Move it to files of
its own, or to [resource snippets](customizing.md#resource-snippets): perseid never overwrites
files without its `@generated` marker.

## Known differences

| Stainless | perseid |
|---|---|
| Resources nested at any depth, methods on the client (`$client`) | One level of resources, from the spec's first tag |
| Types namespaced by resource | Types named after the spec's schemas |
| Every request retried, POST included, on connection errors, 408, 409, 429 and 5xx | POST retried only with an `Idempotency-Key`: `idempotency_keys = true` sends one with every POST. 409 is not retried |
| `environment` option between named base URLs | One default base URL, overridden by `baseURL` / `base_url` or `KNOCK_BASE_URL` |
| Custom client options, sent as headers or parameters | Default headers, or a parameter on each call |
| Pagination by next-page URL, backwards, or in the body | Forward, by a query parameter |
| `stream: true` on a method | A `..._stream` twin method, `createStream()` |
| Webhook `unwrap()` | The Standard Webhooks verifier, with `webhooks = true` |
| Positional parameters set per method | Path parameters positional, the rest as one object or keywords |
| Kotlin, Ruby, PHP, CLI, Terraform, MCP server | Not generated |
| `x-stainless-*` extensions | Ignored: use `x-pagination` and `x-perseid-name` |
